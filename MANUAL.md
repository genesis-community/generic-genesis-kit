# Generic Genesis Kit for BOSH

This is a generic Genesis Kit. It is intended to be used as a starting point
for creating new kits, or wrapping existing bosh deployment manifests that
don't need a dedicated kit.

## Usage

To use this kit, you will need to create a new genesis repsitory using the
`genesis init -k generic` command.  You can then copy your bosh deployment
manifest and any operations files into the ops subdirectory of the new
deployment repository.

### Example - create a new genesis repository based on cloudfoundry/postgres

```bash
git clone https://github.com/cloudfoundry/postgres-release.git postgres-release
genesis init -k generic -d postgres postgres
cp -R postgres-release/templates postgres/ops
genesis new postgres/my-postgres
```

## Customizing

By default, this kit expects there to be a `base.yml` or a `<type>.yml` file in
the `ops` directory, where <type> is the name of the repository you specified
in the `genesis init` command.  Further customization can be done by adding
additional operations files located in the `ops` directory to the `features`
block inside the environment YAML file that was generated by the `genesis new`
command (e.g. `postgres/my-postgres.yml` in the example above).

Other customizations can be made by modifying other blocks in the environment
YAML file.  These include:

### params block

By default, the parameters supported by the `generic` kit are
`params.stemcell_os` and `params.stemcell_version`.  These are used to override
the stemcell OS and version specified in the kit if the manifest doesn't
specify its own set.

You can further customize the `params` block to include any additional parameters
if you want to reference them in files in the `ops` directory, by using the
`spruce (( grab ... ))` operator.  However, since most bosh release templates
already use bosh variables for this purpose, it is easier just to use the
`bosh-variables` block.

### bosh-variables block

The `bosh-variables` block is used to specify the variables that are passed to
the bosh director when deploying the manifest.  Ranther than have a separate
file for bosh variables, or specifying them individually in the deploy command,
you can specify them in the `bosh-variables` block.

Just create a `bosh-variables` block in the environment YAML file, and specify
each variable as a key-value pair.

### instance_groups block

Since the environment YAML file is just fragment of the overall bosh deployment
manifest, you can specify the `instance_groups` block to customize any of the
instance groups in the manifest.  This is useful for specifying the number of
instances, or the VM or persistant disk types for a particular instance group,
or any other properties that are specific to an instance group.

## NOTE:

Genesis is very much based on the idea of convention over configuration.  This
means that it expects certain things to be in certain places, and to be named
in a certain way.

In particular, it expects the bosh director to be named the same as the
environment you're deploying.  In the example above, we used `my-postgres` as
the name of the environment, so genesis expects to use the `my-postgres` bosh
director.  Since you probably don't have a bosh director named `my-postgres`,
you can specify the `bosh_env` under the `genesis` block in the environment
to specify the name of the director as specified in your bosh configuration.
